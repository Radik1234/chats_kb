# Техническое задание  
## База знаний на основе экспорта чатов (v1)

**Версия:** 1.0  
**Дата:** 2026‑09‑07  
**Статус:** черновик для первой итерации

***

## 1. Цель и границы проекта

### 1.1. Цель

Создать локальную систему базы знаний (БЗ) на основе истории групповых чатов (Telegram), которая:

- импортирует и индексирует сообщения из экспорта чата;
- строит семантический поиск и граф знаний;
- предоставляет AI‑агентам доступ к БЗ через **MCP**;
- полностью работает на одном хосте в Docker‑контейнерах с использованием:
  - **Beever Atlas** (бэкенд, хранилища, MCP‑сервер);
  - **llama.cpp server** (локальная LLM);
  - локальной embedding‑модели.

### 1.2. Границы (v1)

В первой версии:

- Поддерживается **один источник**: экспорт Telegram‑группы в JSON.
- Импорт — **пакетный** (загрузка файла/файлов через UI/API Beever Atlas).
- MCP используется для:
  - поиска по БЗ;
  - получения тредов/контекста вокруг сообщений;
  - запроса саммари/структурирования обсуждений.
- Не реализуется:
  - автоматическая синхронизация в реальном времени (live‑бридж);
  - мульти‑тенантность и разграничение прав;
  - интеграция с внешними системами (Jira, Confluence и т.п.).

## 2. Архитектура решения

### 2.1. Компоненты

Система разворачивается на одном хосте в Docker и состоит из следующих компонентов:

1. **Beever Atlas**
   - Бэкенд (FastAPI + ADK‑агенты).
   - Веб‑дашборд (React).
   - MCP‑сервер (28 инструментов для работы с БЗ).
   - Хранилища:
     - **Weaviate** — семантическая память (векторный поиск).
     - **Neo4j** — граф знаний (сущности, связи, решения).
     - **MongoDB** — состояние, кэш вики, конфигурация.
     - **Redis** — сессии/кеши.  
 [mcpservers](https://mcpservers.org/servers/beever-ai/beever-atlas)

2. **llama.cpp server**
   - HTTP‑сервер с OpenAI‑совместимым API (`/v1/chat/completions`, `/v1/embeddings`).
   - Используется для:
     - LLM‑вызовов (дистилляция, саммари, QA).
     - (опционально) эмбеддингов, если embedding‑модель также запускается в llama.cpp.

3. **Embedding‑сервис** (опционально отдельный контейнер)
   - Если embedding‑модель не запускается в том же llama.cpp.
   - OpenAI‑совместимый endpoint для векторизации текстов.

4. **Reverse proxy** (опционально, но рекомендуется)
   - Nginx / Traefik / Caddy.
   - TLS‑терминация.
   - Роутинг:
     - `atlas.example.com` → Beever Atlas UI/API.
     - `llm.example.com` → llama.cpp server.
     - `mcp.example.com` → MCP‑эндпоинт Beever Atlas.

### 2.2. Схема взаимодействия

- Пользователь:
  - работает с дашбордом Beever Atlas (импорт, просмотр вики, поиск);
  - использует внешний AI‑агент (через MCP) для работы с БЗ.
- AI‑агент:
  - подключается к MCP‑серверу Beever Atlas;
  - вызывает тулзы:
    - поиск по сообщениям/вики;
    - получение тредов/контекста;
    - запрос саммари/структурирования.
- Beever Atlas:
  - использует локальную LLM (llama.cpp) для:
    - извлечения фактов из сообщений;
    - построения графа знаний;
    - генерации ответов QA.
  - использует embedding‑модель для:
    - векторизации сообщений;
    - семантического поиска в Weaviate.

## 3. Требования к хосту

### 3.1. Минимальные (демо / небольшой чат)

- **CPU**: 8 vCPU.
- **RAM**: 32 ГБ.
- **GPU**: опционально (для ускорения LLM).
- **Диск**: 100 ГБ SSD.

### 3.2. Рекомендуемые (продакшен, 3000+ участников)

- **CPU**: 12–16 vCPU.
- **RAM**: 48–64 ГБ.
- **GPU**: 1× 12–16 ГБ VRAM (L4, L40S, A10, RTX‑класс).
- **Диск**: 150–250 ГБ SSD.

### 3.3. ОС и ПО

- Linux (Ubuntu 22.04 / 24.04 или аналог).
- Docker Engine 24+ и Docker Compose v2.
- git, curl, make (опционально).

## 4. Функциональные требования

### 4.1. Импорт данных

**FR‑1.** Система должна поддерживать импорт истории чата из JSON‑экспорта Telegram.

- Формат входа: один или несколько JSON‑файлов в формате Telegram Desktop export.
- Загрузка:
  - через веб‑дашборд Beever Atlas (drag‑and‑drop / выбор файла);
  - (опционально) через API (POST с файлом).
- После загрузки:
  - сообщения парсятся и сохраняются в MongoDB;
  - запускается пайплайн дистилляции (LLM) и векторизации (embeddings);
  - данные индексируются в Weaviate и Neo4j. [mcpservers](https://mcpservers.org/servers/beever-ai/beever-atlas)

**FR‑2.** Система должна корректно обрабатывать:

- текстовые сообщения;
- метаданные (user_id, timestamp, reply_to_message_id);
- вложения (как минимум — ссылки на файлы/изображения; хранение медиа — опционально).

### 4.2. Поиск и навигация

**FR‑3.** Система должна обеспечивать:

- **Полнотекстовый поиск** по тексту сообщений (keyword).
- **Семантический поиск** через Weaviate (по эмбеддингам).
- Поиск по:
  - участникам;
  - временным диапазонам;
  - ключевым словам (например, `cputime`).

**FR‑4.** Система должна предоставлять возможность:

- находить сообщение по ключевому запросу;
- получать «трёд/обсуждение» вокруг сообщения:
  - сообщения, ссылающиеся на данное (`reply_to_message_id`);
  - сообщения в заданном временном окне (±N часов/дней).

### 4.3. База знаний и вики

**FR‑5.** Система должна автоматически формировать вики‑страницы на основе чатов:

- темы/проблемы;
- решения;
- участники/эксперты;
- ключевые параметры (версии, окружение, конфигурации).

**FR‑6.** Вики должна быть доступна через:

- веб‑дашборд;
- MCP‑тулзы (чтение страниц, разделов, списков тем).

### 4.4. AI‑агент и MCP

**FR‑7.** Система должна предоставлять MCP‑сервер с инструментами для:

- поиска по сообщениям и вики;
- получения тредов/контекста;
- чтения вики (страницы, разделы);
- запроса саммари/структурирования обсуждений.

**FR‑8.** Внешний AI‑агент должен иметь возможность:

- подключиться к MCP‑серверу по HTTP (streamable‑http transport);
- использовать предоставленные тулзы для:
  - поиска по ключевым словам (например, `cputime`);
  - получения списка релевантных сообщений;
  - получения структурированного саммари проблемы и обсуждения.

### 4.5. Локальная LLM и эмбеддинги

**FR‑9.** Все вызовы LLM должны идти на локальный llama.cpp server:

- модель — instruct‑версия (7B–14B, Q4 или выше);
- контекст — не менее 8k токенов (желательно 16k+).

**FR‑10.** Эмбеддинги должны генерироваться локальной моделью:

- мультиязычная (поддержка русского);
- размерность вектора — согласована со схемой Weaviate (например, 1024 для bge‑m3).

## 5. Нефункциональные требования

### 5.1. Безопасность

**NFR‑1.** Все сервисы должны быть доступны только с локального хоста или через reverse proxy с TLS.

**NFR‑2.** Доступ к MCP‑серверу должен быть защищён:

- API‑ключи (BEEVER_MCP_API_KEYS);
- передача ключей только по HTTPS.

**NFR‑3.** Данные (история чата, индексы, модели) хранятся локально, без отправки третьим сторонам.

### 5.2. Надёжность и производительность

**NFR‑4.** Система должна поддерживать:

- минимум 100k сообщений в БЗ без критической деградации;
- время ответа на поисковый запрос — до 2–3 секунд (p95) при нормальной нагрузке.

**NFR‑5.** Должна быть предусмотрена возможность:

- бэкапа MongoDB, Neo4j, Weaviate (дампы/снэпшоты);
- восстановления из бэкапа.

### 5.3. Эксплуатация

**NFR‑6.** Развёртывание должно выполняться через `docker compose up -d`.

**NFR‑7.** Конфигурация (модели, ключи, endpoint’ы) должна задаваться через `.env`‑файлы.

**NFR‑8.** Должна быть предусмотрена базовая документация:

- как развернуть;
- как импортировать чат;
- как подключить MCP‑агент.

## 6. Стек технологий

- **Контейнеризация**: Docker, Docker Compose.
- **Бэкенд БЗ**: Beever Atlas (FastAPI + ADK).
- **Хранилища**:
  - Weaviate (векторная БД);
  - Neo4j (граф знаний);
  - MongoDB (документы, состояние);
  - Redis (кеши, сессии).
- **LLM**: llama.cpp server (GGUF‑модель, OpenAI‑совместимый API).
- **Embeddings**: llama.cpp server или отдельный сервис (OpenAI‑совместимый API).
- **MCP**: встроенный MCP‑сервер Beever Atlas (streamable‑http). [mcpservers](https://mcpservers.org/servers/beever-ai/beever-atlas)
- **Reverse proxy**: Nginx / Traefik / Caddy (опционально, но рекомендуется).

## 7. Этапы реализации

### Этап 1. Инфраструктура и базовое развёртывание

**Задачи:**

1. Подготовить хост (ОС, Docker, Docker Compose).
2. Создать структуру репозитория / каталогов:
   - `docker-compose.yml`;
   - `.env` (шаблон + пример);
   - папки для данных (`./data/weaviate`, `./data/neo4j`, `./data/mongo`, `./data/redis`);
   - папка для моделей (`./models`).
3. Настроить `docker-compose.yml`:
   - сервисы Beever Atlas (backend, bot, web, weaviate, neo4j, mongo, redis);
   - сервис llama.cpp server;
   - (опционально) reverse proxy.
4. Подобрать и скачать модели:
   - LLM (например, Qwen2.5‑14B‑Instruct, GGUF Q4);
   - embedding (например, bge‑m3, GGUF).
5. Настроить `.env`:
   - URL и ключи для LLM (llama.cpp);
   - URL и ключи для embeddings;
   - ключи доступа к MCP;
   - параметры Weaviate/Neo4j/Mongo/Redis.

**Критерии приёмки:**

- `docker compose up -d` разворачивает все сервисы;
- дашборд Beever Atlas доступен по HTTP/HTTPS;
- llama.cpp server отвечает на `/v1/chat/completions` и `/v1/embeddings`.

***

### Этап 2. Импорт чата и базовая индексация

**Задачи:**

1. Подготовить тестовый экспорт Telegram‑группы (JSON).
2. Загрузить экспорт через дашборд Beever Atlas:
   - проверить, что сообщения отображаются;
   - проверить, что запускается пайплайн дистилляции.
3. Настроить пайплайн:
   - использование локальной LLM (llama.cpp);
   - использование локальной embedding‑модели.
4. Проверить индексы:
   - поиск по ключевым словам в UI;
   - семантический поиск (по смыслу запроса).

**Критерии приёмки:**

- История чата импортирована и отображается в дашборде;
- Поиск по ключевым словам (например, `cputime`) находит релевантные сообщения;
- Семантический поиск работает (запрос на естественном языке находит релевантные сообщения).

***

### Этап 3. MCP и интеграция с AI‑агентом

**Задачи:**

1. Включить MCP‑сервер Beever Atlas:
   - сгенерировать MCP‑ключи;
   - настроить transport (streamable‑http).
2. Настроить внешний AI‑агент (например, Claude Code / Cursor / кастомный агент):
   - прописать конфиг MCP (URL, ключи);
   - проверить видимость тулзов Beever Atlas.
3. Реализовать сценарии использования:
   - поиск по ключевому слову (`cputime`);
   - получение тредов/контекста вокруг сообщения;
   - запрос саммари обсуждения проблемы.

**Критерии приёмки:**

- AI‑агент видит MCP‑сервер Beever Atlas;
- агент успешно вызывает тулзы поиска и чтения вики;
- агент получает структурированные ответы на основе истории чата.

***

### Этап 4. Документация и эксплуатация

**Задачи:**

1. Написать краткую документацию:
   - как развернуть стек;
   - как импортировать чат;
   - как подключить MCP‑агент;
   - как добавлять новые чаты/обновлять экспорт.
2. Описать процедуру бэкапа/восстановления:
   - какие директории/сервисы бэкапить;
   - пример команд для дампа/рестора.
3. Зафиксировать параметры моделей и конфигурацию:
   - названия моделей, версии, параметры запуска llama.cpp;
   - параметры `.env`.

**Критерии приёмки:**

- Документация доступна в репозитории (README.md + разделы);
- Новый разработчик может развернуть систему по инструкции без дополнительных пояснений.

## 8. Риски и ограничения

- **Качество локальной LLM** может быть ниже облачных аналогов; может потребоваться подбор модели/параметров.
- **Производительность CPU‑only** может быть недостаточной для интерактива при больших моделях; рекомендуется GPU.
- **Формат экспорта Telegram** может меняться; может потребоваться адаптация парсеров.
- **API Beever Atlas** в версии 0.x может быть нестабильным; возможны изменения в схемах и тулзах MCP. [mcpservers](https://mcpservers.org/servers/beever-ai/beever-atlas)

***

## 9. Критерии приёмки проекта (v1)

Проект считается реализованным, если:

1. Развёрнут полный стек в Docker на одном хосте:
   - Beever Atlas + хранилища;
   - llama.cpp server;
   - (опционально) reverse proxy.
2. Импортирован тестовый экспорт Telegram‑группы:
   - сообщения отображаются в дашборде;
   - работает поиск по ключевым словам и семантический поиск.
3. MCP‑сервер Beever Atlas настроен и доступен:
   - внешний AI‑агент подключается и видит тулзы;
   - агент успешно выполняет поиск по БЗ и получает саммари обсуждений.
4. Написана базовая документация по развёртыванию и эксплуатации.
