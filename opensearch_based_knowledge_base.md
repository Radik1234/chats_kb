# Техническое задание

## База знаний на основе истории чатов Telegram (OpenSearch‑based)

**Версия:** 1.0\
**Дата:** 2026‑09‑16\
**Статус:** черновик для первой итерации

______________________________________________________________________

## 1. Цель и контекст проекта

### 1.1. Цель

Создать базу знаний (БЗ) на основе истории групповых чатов Telegram, которая:

- хранит и индексирует сообщения чата в **OpenSearch**;
- предоставляет AI‑агентам и субагентам доступ к данным через набор **skills** (поиск, выборка тредов, контекст для LLM);
- позволяет эффективно отбирать релевантные сообщения и исключать спам/шум перед отправкой в онлайн‑модели (например, DeepSeek Flash);
- разворачивается локально (MVP), а затем мигрирует в облачную инфраструктуру для production.


### 1.2. Контекст

- Есть опыт развёртывания MVP на Beever Atlas.
- Выявлены проблемы:
    - низкая производительность локальной LLM для дистилляции;
    - желание перейти на онлайн‑модели, но с жёстким контролем объёма контекста.
- У команды есть экспертиза по **OpenSearch / Elasticsearch**, DevOps, AI‑агентам.

______________________________________________________________________

## 2. Границы проекта (v1)

В первой версии:

- Поддерживается **один источник**: экспорт одного Telegram‑чата (группы/канала) в JSON.
- Импорт — **пакетный** (загрузка файлов экспорта).
- Skills для агентов:
    - поиск по сообщениям;
    - получение тредов/контекста;
    - формирование контекста для онлайн‑модели.
- Не реализуется в v1:
    - live‑синхронизация с Telegram (бот/бридж);
    - мульти‑тенантность и разграничение прав;
    - интеграция с внешними системами (Jira, Confluence и т.п.).

## 3. Архитектура решения

### 3.1. Компоненты

Система состоит из следующих основных компонентов:

1. **OpenSearch кластер**
    - Хранение и индексация:
        - сырых сообщений;
        - эмбеддингов;
        - фактов/проблем/решений (опционально).
    - Поиск:
        - полнотекстовый (BM25);
        - векторный (kNN);
        - гибридный (RRF / script_score).
2. **Сервис импорта и индексации**
    - Парсинг JSON‑экспорта Telegram.
    - Нормализация сообщений.
    - Вычисление эмбеддингов (локальной моделью).
    - Загрузка в OpenSearch.
3. **Skills‑сервис для AI‑агентов**
    - API для:
        - поиска по сообщениям;
        - получения тредов;
        - выборки фактов/проблем;
        - формирования контекста для LLM.
    - Реализация логики:
        - hybrid search;
        - rerank;
        - spam/noise filter;
        - context builder.
4. **UI (опционально, минимальный)**
    - Просмотр:
        - списка каналов/чатов;
        - сообщений по запросу;
        - статистики (объём данных, активность).
    - Загрузка новых экспортов (если не через API напрямую).
5. **AI‑агенты и субагенты**
    - Внешние агенты (например, на базе DeepSeek Flash и других онлайн‑моделей).
    - Используют skills‑сервис через HTTP/MCP для:
        - поиска информации;
        - получения контекста;
        - генерации ответов/саммари.

### 3.2. Схема взаимодействия

- Пользователь → AI‑агент (например, через чат‑интерфейс).
- AI‑агент → Skills‑сервис:
    - вызывает `search_messages`, `get_thread`, `build_context_for_llm`.
- Skills‑сервис → OpenSearch:
    - выполняет поисковые запросы;
    - применяет rerank и фильтры;
    - возвращает отобранные сообщения.
- AI‑агент → Онлайн‑модель:
    - отправляет запрос + компактный контекст;
    - получает ответ/саммари.

## 4. Требования к хосту (MVP / локальная версия)

### 4.1. Минимальные (демо / небольшой чат)

- **CPU**: 4–6 vCPU.
- **RAM**: 16–24 ГБ.
- **Диск**: 80–120 ГБ SSD.
- **GPU**: опционально (для ускорения эмбеддингов).


### 4.2. Рекомендуемые (MVP на одном чате, 3000+ участников)

- **CPU**: 8–12 vCPU.
- **RAM**: 32–48 ГБ.
- **Диск**: 150–250 ГБ SSD.
- **GPU**: 1× 8–12 ГБ VRAM (для эмбеддингов / локальной LLM, если останется).


### 4.3. ОС и ПО

- Linux (Ubuntu 22.04 / 24.04 или аналог).
- Docker Engine 24+ и Docker Compose v2.
- git, curl, make (опционально).

## 5. Функциональные требования

### 5.1. Импорт данных

**FR‑1.** Система должна поддерживать импорт истории чата из JSON‑экспорта Telegram.

- Формат входа: один или несколько JSON‑файлов в формате Telegram Desktop export.
- Загрузка:
    - через API skills‑сервиса (POST с файлом);
    - (опционально) через минимальный UI.
- После загрузки:
    - сообщения парсятся и нормализуются;
    - вычисляются эмбеддинги (локальной моделью);
    - данные индексируются в OpenSearch.

**FR‑2.** Система должна корректно обрабатывать:

- текстовые сообщения;
- метаданные (user_id, user_name, timestamp, reply_to_message_id);
- базовые признаки:
    - `is_bot` (по известному списку ботов);
    - `has_links`, `has_logs` (по паттернам в тексте);
    - `error_codes` (извлечённые из текста, например `TimeoutException`).


### 5.2. Поиск и навигация

**FR‑3.** Система должна обеспечивать:

- **Полнотекстовый поиск** по тексту сообщений (BM25).
- **Векторный поиск** через kNN (по эмбеддингам).
- **Гибридный поиск**:
    - комбинация text + knn;
    - возможность настройки весов, boosting по полям.

**FR‑4.** Система должна предоставлять возможность:

- поиска по:
    - ключевым словам (например, `cputime`);
    - участникам (`user_id`, `user_name`);
    - временным диапазонам;
    - наличию логов/ошибок.
- получения списка релевантных сообщений с метаданными и подсветкой совпадений.

**FR‑5.** Система должна поддерживать:

- поиск тредов/обсуждений вокруг сообщения:
    - по `reply_to_message_id`;
    - по временному окну (±N часов/дней);
    - с ограничением на число сообщений.


### 5.3. Skills для AI‑агентов

**FR‑6.** Система должна предоставлять skills (HTTP API / MCP) для:

1. `search_messages`
    - Вход:
        - `query` (текст);
        - `filters` (user_id, time_range, has_logs, is_bot и т.п.);
        - `top_k` (число результатов).
    - Логика:
        - hybrid search (BM25 + kNN);
        - rerank (cross‑encoder или упрощённый scoring);
        - spam/noise filter (по правилам).
    - Выход:
        - список сообщений (id, текст, пользователь, timestamp, score).
2. `get_thread`
    - Вход:
        - `message_id`;
        - `time_window` (±N часов);
        - `max_messages`.
    - Логика:
        - поиск сообщений, связанных с `message_id` (через `reply_to_message_id`);
        - сортировка по времени;
        - фильтрация спама.
    - Выход:
        - список сообщений треда.
3. `get_facts` (опционально, v1.1+)
    - Вход:
        - `topic` / `keyword`;
        - `top_k`.
    - Логика:
        - поиск по индексу фактов/проблем/решений.
    - Выход:
        - список фактов с ссылками на сообщения.
4. `build_context_for_llm`
    - Вход:
        - список сообщений;
        - `task_type` (проблема, решение, общий вопрос);
        - `max_tokens` (лимит на контекст).
    - Логика:
        - группировка по тредам/темам;
        - отбор ключевых цитат;
        - формирование компактного текста контекста.
    - Выход:
        - текст контекста для онлайн‑модели.

**FR‑7.** Skills должны быть спроектированы так, чтобы их могли использовать:

- основной AI‑агент;
- субагенты (например, отдельный агент по поиску, отдельный — по саммари).


### 5.4. UI (опционально)

**FR‑8.** Если реализуется UI, он должен предоставлять:

- просмотр:
    - списка чатов/каналов;
    - сообщений по запросу (поиск, фильтры);
    - базовой статистики (число сообщений, активность по времени).
- загрузку новых экспортов (через форму / drag‑and‑drop).

UI не является критичным для v1 и может быть минимальным или отложен до v1.1.

## 6. Нефункциональные требования

### 6.1. Безопасность

**NFR‑1.** Все сервисы должны быть доступны:

- либо только с локального хоста;
- либо через reverse proxy с TLS (в production).

**NFR‑2.** Доступ к skills‑API должен быть защищён:

- API‑ключи / токены;
- передача только по HTTPS (в production).

**NFR‑3.** Данные (история чата, индексы, модели) хранятся локально (MVP) и в контролируемом облаке (production), без отправки третьим сторонам, за исключением вызовов онлайн‑моделей по явным запросам агентов.

### 6.2. Надёжность и производительность

**NFR‑4.** Система должна поддерживать:

- минимум 100k сообщений в индексе без критической деградации;
- время ответа на поисковый запрос — до 1–2 секунд (p95) при нормальной нагрузке.

**NFR‑5.** Должна быть предусмотрена возможность:

- бэкапа индексов OpenSearch (snapshot/restore);
- восстановления из бэкапа.


### 6.3. Эксплуатация

**NFR‑6.** Развёртывание должно выполняться через `docker compose up -d` (MVP).

**NFR‑7.** Конфигурация (эндпоинты, ключи, параметры поиска) должна задаваться через `.env`‑файлы и/или конфиги.

**NFR‑8.** Должна быть предусмотрена базовая документация:

- как развернуть;
- как импортировать чат;
- как использовать skills из агентов.

## 7. Стек технологий

- **Контейнеризация**: Docker, Docker Compose.
- **Поисковый движок**: OpenSearch (2.x / 3.x).
- **Хранилище**:
    - OpenSearch индексы:
        - `messages` (сырые сообщения + эмбеддинги);
        - `threads` (опционально);
        - `facts` / `problems` / `solutions` (опционально, v1.1+).
- **Embeddings**:
    - локальная модель (например, bge‑m3, multilingual‑e5) через:
        - отдельный сервис (FastAPI + transformers / sentence‑transformers);
        - или llama.cpp server с embedding‑моделью.
- **Skills‑сервис**:
    - язык: Python или TypeScript (по выбору команды);
    - фреймворк: FastAPI / Express;
    - доступ к OpenSearch через официальный клиент.
- **UI** (опционально):
    - легкий фронтенд (React / Vue) или простой admin‑UI.
- **Reverse proxy**:
    - Nginx / Traefik / Caddy (для production).

## 8. Этапы реализации

### Этап 1. Ядро (Core)

**Цель:** развернуть базовую инфраструктуру и реализовать основные компоненты.

**Задачи:**

1. Подготовить хост (ОС, Docker, Docker Compose).
2. Создать структуру репозитория / каталогов:
    - `docker-compose.yml`;
    - `.env.example`, `.env`;
    - папки для данных (`./data/opensearch`);
    - папка для моделей (`./models`);
    - папки для сервисов (`./services/import`, `./services/skills`, `./services/embeddings`).
3. Настроить `docker-compose.yml`:
    - сервис OpenSearch (single‑node для MVP);
    - сервис embeddings (локальная модель);
    - сервис skills‑API;
    - (опционально) сервис импорта как отдельный контейнер.
4. Спроектировать и создать индексы OpenSearch:
    - `messages`:
        - маппинг полей (text, keyword, date, boolean, vector);
        - настройка анализаторов (русский язык);
        - kNN‑параметры (размерность вектора, метод).
    - (опционально) `threads`, `facts`.
5. Реализовать базовый skills‑сервис:
    - эндпоинты:
        - `POST /search_messages`;
        - `POST /get_thread`;
        - `POST /build_context_for_llm`.
    - базовая логика:
        - простые запросы к OpenSearch;
        - фильтрация по полям;
        - формирование ответа.

**Критерии приёмки:**

- `docker compose up -d` разворачивает все сервисы;
- OpenSearch доступен, индексы созданы;
- skills‑сервис отвечает на базовые запросы (поиск по тексту, получение треда).

### Этап 3. Наполнение данными одного чата

**Цель:** загрузить историю одного Telegram‑чата и отработать пайплайн индексации.

**Задачи:**

1. Подготовить тестовый экспорт Telegram‑группы (JSON).
2. Реализовать сервис/скрипт импорта:
    - парсинг JSON;
    - нормализация сообщений:
        - приведение к единой схеме;
        - вычисление производных полей (`has_links`, `has_logs`, `error_codes`);
    - вычисление эмбеддингов:
        - вызов embeddings‑сервиса;
        - сохранение векторов.
    - загрузка в OpenSearch:
        - bulk‑индексация;
        - обработка ошибок и повторные попытки.
3. Настроить параметры индексации:
    - размер батчей;
    - параллелизм;
    - логирование прогресса.
4. Провести пробную загрузку:
    - небольшой период (например, 1–2 недели);
    - проверка корректности данных в OpenSearch;
    - проверка поиска через skills‑API.

**Критерии приёмки:**

- История чата импортирована и отображается в OpenSearch;
- Поиск по ключевым словам (например, `cputime`) находит релевантные сообщения;
- Векторный поиск работает (запрос на естественном языке находит релевантные сообщения).

### Этап 4. Агентский доступ (Skills для AI‑агентов)

**Цель:** предоставить AI‑агентам и субагентам удобный доступ к данным через skills.

**Задачи:**

1. Доработать skills‑сервис:
    - реализовать полноценный `search_messages`:
        - hybrid search (BM25 + kNN);
        - rerank (cross‑encoder или упрощённый scoring);
        - spam/noise filter (правила по ботам, ссылкам, типичному спаму).
    - реализовать `get_thread`:
        - выборка тредов по `reply_to_message_id`;
        - фильтрация и сортировка;
        - ограничение по числу сообщений.
    - реализовать `build_context_for_llm`:
        - группировка сообщений;
        - отбор ключевых цитат;
        - формирование компактного контекста с лимитом токенов.
2. Документировать API skills:
    - спецификация эндпоинтов;
    - примеры запросов/ответов;
    - рекомендации по использованию из агентов.
3. Интегрировать skills с AI‑агентом(ами):
    - настроить вызовы skills из основного агента;
    - при необходимости реализовать субагентов:
        - агент поиска;
        - агент саммари;
        - агент по работе с конкретными доменами (например, только технические проблемы).
4. Провести тестовые сценарии:
    - поиск по ключевым словам (`cputime`);
    - получение тредов вокруг конкретных сообщений;
    - формирование контекста и отправка в онлайн‑модель (DeepSeek Flash или аналог);
    - оценка качества ответов и объёма токенов.

**Критерии приёмки:**

- AI‑агент успешно вызывает skills через API;
- агент получает релевантные сообщения и треды;
- контекст для онлайн‑модели существенно сокращён по сравнению с «сырой» историей;
- качество ответов агента устраивает заказчиков.

### Этап 5. Миграция в облачную инфраструктуру

**Цель:** перенести MVP из локального хоста в облако, подготовить к production.

**Задачи:**

1. Выбрать облачного провайдера:
    - варианты:
        - управляемый OpenSearch (AWS OpenSearch Service, Elastic Cloud и т.п.);
        - self‑managed OpenSearch на VM (например, в Yandex Cloud, Selectel, Timeweb Cloud и др.).
2. Спроектировать облачную архитектуру:
    - кластер OpenSearch:
        - количество нод;
        - тип инстансов;
        - хранение (SSD, размер);
    - сервисы:
        - skills‑сервис;
        - embeddings‑сервис (если остаётся локальным или переносится);
        - reverse proxy / ingress;
    - сеть:
        - VPC, подсети;
        - security groups / firewall rules.
3. Реализовать инфраструктуру как код (IaC):
    - Terraform / Pulumi / другой инструмент;
    - описание:
        - кластера OpenSearch;
        - VM / контейнеров для сервисов;
        - сетевых правил.
4. Настроить CI/CD:
    - пайплайны для:
        - деплоя сервисов;
        - миграции индексов (snapshot/restore или reindex);
        - обновления конфигураций.
5. Перенести данные:
    - создать snapshot локального OpenSearch;
    - восстановить snapshot в облачном кластере;
    - либо выполнить reindex через API.
6. Настроить мониторинг и алерты:
    - метрики OpenSearch (CPU, RAM, disk, query latency);
    - метрики сервисов (RPS, latency, ошибки);
    - алерты при превышении порогов.

**Критерии приёмки:**

- Система развёрнута в облаке;
- Данные успешно перенесены;
- Skills‑сервис доступен из облачной сети;
- Настроен базовый мониторинг и алерты.

### Этап 6. Production

**Цель:** довести систему до уровня, пригодного для постоянной эксплуатации.

**Задачи:**

## 9. Риски и ограничения

- **Качество поиска** может зависеть от:
    - выбранной embedding‑модели;
    - настроек гибридного поиска и rerank.
- **Спам и шум** в Telegram‑чате могут быть разнообразными;
    - правила фильтрации потребуют итеративной доработки.
- **API и возможности OpenSearch**:
    - нужно внимательно следить за версиями и совместимостью (2.x vs 3.x).
- **Миграция в облако** может потребовать:
    - дополнительных затрат на инфраструктуру;
    - времени на отладку сети и безопасности.
